## 3. `export_pair/` 的定義

`export_pair/` 表示「交給第二部分的底圖＋待修補 Mask」，是可以重建的交接資料，不是必須跑完偵測才存在的資料。

| 來源 | 根目錄底圖 | `other_mask/` | 第一部分資料 |
| --- | --- | --- | --- |
| 原圖經第一部分編輯 | 原圖疊加確認後的純色填充 overlay | 確認後的待修補 Mask | 保存 overlay、other、edited |
| 新項目直接匯入 Mask | 原圖轉為規範化的 RGB PNG，維持像素座標 | 匯入、驗證並確認後的 Mask | 無需執行偵測；填色層為空 |
| 已有編輯的項目更換 Mask | 保留現有填色形成的底圖 | 新匯入 Mask 建立新修訂；不默默清除既有人工狀態 | 在套用前顯示替換影響，衝突交由使用者確認 |

來源原件保持不變。解碼、色彩通道及方向正規化必須記錄；不得單獨旋轉圖片而不轉換同組 Mask。尺寸或方向無法可靠對齊時拒絕進入推理。

`colored/` 如有生成，只是彩色提示預覽，不能成為 GPU 輸入。RF 全部文字偵測 Mask 也不能替代人工確認後的 `other_mask`。

配對沿用現有規則：第一層圖片、忽略 `._*`、按 stem 配對、拒絕重複 stem／缺少配對／格式錯誤／尺寸不同。缺少 Mask 不等於全黑 Mask。

### 不需要修復的頁面

- 按與批次器一致的二值化規則判定 Mask，白色代表修補，黑色代表保留。
- 全黑 Mask 跳過所有選中模型，將該次底圖保存為各工作流的對應結果並記錄 `passthrough`；不是退回可能仍有文字的原始圖片。
- 第三部分將這些頁面視為已備妥的底圖成品，不要求逐頁手動選擇。
- 一整批全黑時直接生成完整輸出，不載入修復模型，不等待 ComfyUI 可用。
- 進度分開顯示總頁數、需推理頁數、直接沿用頁數。成功條件仍是結果頁面完整。
- 比較 PDF 沿用既有約定：不為全黑 Mask 頁建立頁面。

## 4. 資料與版本

### 責任分離

| 資料 | 責任與主要內容 |
| --- | --- |
| Project | ID、名稱、格式版本、頁面清單、目前編輯修訂、修復紀錄、選定的結果與合成紀錄 |
| Page | 穩定 page ID、原檔名與輸出 stem、順序、尺寸、原件及工作圖內容雜湊 |
| Edit revision | 純色 overlay、待修補 Mask、人工修改／擦除保護、偵測設定及模型版本 |
| Input snapshot | 提交時固定的底圖、Mask、頁面映射及內容雜湊；提交後不可覆寫 |
| GPU job | 種類（偵測或修復）、project ID、輸入修訂、狀態、完成頁面、錯誤及日誌 |
| Composition | 綁定一個修復 run 和其底圖；候選來源、像素分配、差異設定、羽化與逐頁確認狀態 |

沿用磁碟檔案＋JSON 持久化，不為這次擴充引入資料庫。大型像素資料用影像或無 pickle 的 NPZ 保存，JSON 保存索引。頁面資產先寫入新版本，再原子更新 manifest，避免 manifest 指向半寫入資料。

保存請求附帶修訂號，舊請求不得覆蓋新編輯。瀏覽器顯示「保存中／已保存／保存失敗」，切頁和導出以伺服器已確認版本為準。

修改底圖或 Mask 形成新修訂；舊候選和合成記錄仍绑定舊快照，不能混用。使用者可以回看舊 run，新的修復結果不覆蓋舊的人工採用區域。

### 伺服器目錄建議

```text
<COMIC_DATA_ROOT>/
├─ projects/<project-id>/
│  ├─ project.json
│  ├─ originals/                     原始上傳，始終保留
│  ├─ assets/                        規範化工作圖、匯入 Mask、縮圖
│  ├─ ctd_inpainted/
│  │  ├─ raw/                        當前編輯索引與 overlay/other/edited
│  │  └─ export_pair/                當前草稿的交接圖，可重建
│  │     ├─ <stem>.png
│  │     └─ other_mask/<stem>.png
│  ├─ revisions/<revision-id>/       可續編輯修訂
│  ├─ inputs/<snapshot-id>/
│  │  ├─ manifest.json
│  │  └─ export_pair/                不可變的修復輸入
│  ├─ compositions/<run-id>/
│  │  ├─ selection.json
│  │  └─ assignments/<stem>.png      原尺寸像素來源分配
│  ├─ result/<composition-id>/       已導出的成品
│  └─ exports/                       可重建的下載包
└─ jobs/<job-id>/                    沿用既有 job.json、結果及日誌
   ├─ job.json
   ├─ inpaint_workflows/
   └─ logs/
```

項目透過 ID 引用既有 jobs，先保留現有第二部分的實際工作目錄和下載端點。不要一邊新增項目功能、一邊搬動所有歷史結果。實作可用內容去重減少重複圖檔，但快照不可變的語意優先，FireRed 的平鋪模型輸入仍必須是真實檔案。

舊 jobs 保持獨立可讀、可下載，不強制轉成項目。新欄位使用相容預設；「舊任務轉項目」列為後續能力，必須先確認確實保有原圖和必要輸入，不能把來源不明的舊底圖自動當成原圖，也不能為遷移重新推理。

完整項目導出時將引用的資產實體收齊，改成封存內相對路徑，不依赖原伺服器的絕對路徑或符號連結。選中 run 的可讀交接布局維持：

```text
ctd_inpainted/export_pair/
├─ <stem>.png
├─ other_mask/<stem>.png
└─ inpaint_workflows/
   ├─ flux2klein_lanpaint/<stem>.png
   ├─ firered/<stem>.png
   ├─ qwen2511_lanpaint/<stem>.png
   └─ <比較PDF，適用時>
```

只建立實際選中的工作流目錄。歷史 run 與修訂在封存內各自保存並由 manifest 引用；日誌在封存頂層 `logs/`，不混入 `inpaint_workflows/`。本次完整項目封存供新網頁重新匯入，不承諾原桌面 GUI 能直接打開全部新版項目狀態；圖像交接格式保持相容。

## 5. 第一部分：RF＋MangaLens 與編輯

### 推理及分類

1. 檢查頁面輸入、權重和 GPU 執行環境，建立偵測任務。
2. RF-DETR 生成原尺寸文字／狀聲詞選區；MangaLens 生成氣泡實例範圍。
3. 沿用現有保守純色判斷，產生填色 overlay 和待修補 other。氣泡無法可靠填色時保留待修補，不強行塗白。
4. 保存偵測快取和正式編輯資料，讓使用者逐頁修正。

現行 RF 的 auto 不會選 CUDA，MangaLens 的呼叫明確指定 CPU；遷入時改為顯式、可檢查的 CUDA 執行路徑。模型缺失或 GPU 不可用時顯示原因，不默默改用 CPU，也不影響直接進第二部分。

### 第一版畫布功能

- 頁面列表與縮圖、原尺寸座標、縮放、平移、適合視窗。
- 原圖、填色預覽、待修補 Mask 的疊加與顯示控制。
- F1 純色填充、F2 圖像修補；兩類互斥，擦除兩類後顯示原圖。
- 矩形、筆刷、添加／擦除、取色或指定填色、撤銷／重做。
- 保存完整顏色、Mask 和人工修改保護。重新偵測只更新未被人工保護的範圍。
- 直接匯入 Mask 時使用同一畫布檢查和修正，不要求執行偵測。
- 單獨導出配對資料，或確認後建立第二部分輸入快照。

魔法棒、多邊形套索、獨立 ROI 編輯視窗、裁切與旋轉不列入第一版。普通編輯不重新跑偵測，也不自動重新分類。

## 6. 第三部分：第二部分之後比較合成

- 從項目中已完成的修復 run 進入；第一版不在未完成 run 上建立合成，不做獨立候選圖匯入。
- 比較底圖必須是該 run 的輸入快照，不使用當前可能已修改的草稿或最初原圖。
- 左側即時成品，右側最多三個候選；候選順序沿用 Flux、FireRed、Qwen。
- 同步縮放、平移、底圖／候選比較滑桿；使用矩形和筆刷採用局部，支持整組採用、恢復底圖及來源顏色顯示。
- 每個候選由「候選與底圖的差異」計算可採用 Mask；獨立於生成 Mask。閾值等只用於人工選區，不作生成品質評分、拒收或自動篩除。
- 保存原尺寸像素來源分配、羽化、撤銷／重做及逐頁確認。重算差異不默默清掉人工選擇。
- 候選尺寸不同時提示不可對齊，不拉伸硬合成；缺頁不可當作全黑 Mask 直接放行。
- 初次打開可按固定順序用第一個可用候選形成預覽，明確標為待確認；全黑頁自動以底圖完成。尚未確認頁可提供批量「採用目前預覽」操作，不能把預覽默默當完成品。
- 成品預覽與伺服器原尺寸导出使用相同合成規則。保存 assignments，僅一份文字摘要不足以重開續編。

## 7. 架構與 GPU 排程

沿用 React＋TypeScript＋Ant Design、FastAPI、6008 和 ComfyUI 6006。Ant Design 承載列表及控制項，Canvas 承載即時圖片互動；畫筆移動先在瀏覽器預覽，完成操作後保存，不逐滑鼠事件等待遠端。

FastAPI 新增項目、頁面圖片／縮圖、修訂、偵測任務、合成與導出 API。CPU 影像運算和打包交給背景執行，不阻塞 API；RF／MangaLens 使用獨立推理程序，不在 FastAPI web worker 裡常駐 CUDA 模型。第一版不要求把兩個模型做成 ComfyUI 節點。

- 偵測和修復共用一個持久化 GPU 調度入口，同一時間僅一個 active GPU job；第一版維持忙碌時拒絕新增 GPU 任務的既有規則，不新增跨項目自動排隊產品功能。
- 同批模型按階段集中執行，優先全批 RF、全批 MangaLens，再做後處理；用持久快取交接，避免每頁反覆冷載入模型。
- 修復前確保偵測程序退出、CUDA 顯存釋放；偵測前協調 ComfyUI 卸載閒置模型。先確認 ComfyUI 沒有正在執行或排隊的外部工作，不重啟 6006 來強行清顯存。
- 保留既有三工作流串行執行、32 GB 目標、固定提示詞和調參。Qwen RGBA、FireRed 真實平鋪檔案、輸出數量與日誌規則不變。
- 前端頁面切換或關閉不取消背景任務。恢復時核對已完成頁面、輸入快照和既有執行狀態，避免盲目重複提交。
- 既有 GPU 活動期間上傳／新提交／歷史 ZIP 的鎖定維持；新增畫布可對已載入的其他草稿保存新修訂，但不得修改 active job 的快照。偵測中的同一頁先鎖定編輯，防止偵測回寫覆蓋人工操作。
- 手工操作與成品合成不觸發推理；第一版不另建獨立 CPU 雲服務，也不自動開關 AutoDL 實例。

## 8. 導出、重開與刪除

### 導出完整項目

包含原圖、已保存編輯、Mask、不可變輸入、已有候選結果、合成來源圖、項目與歷史 run 清單。模型、Python 環境、憑證和可重建縮圖不打包。

首版在無活動寫入的穩定狀態建立完整封存；項目正在偵測／修復／導出或尚有未保存修改時，說明原因並暫停新的完整封存操作。現有「下載目前結果」仍依第二部分規則保留。

封存使用帶版本 manifest、相對路徑及內容雜湊。匯入先驗證完整性、路徑範圍和解壓大小，再分配新 project ID、重映射內部 run 引用，不覆蓋伺服器已有項目，不恢復執行中的 GPU 任務。

### 只導出結果

導出選定合成版本的完整 PNG 集合，按原始 stem 和頁序映射；全黑頁包含在內。不包含原圖、Mask、候選目錄或編輯記錄。未確認頁、缺頁或錯誤阻止標記為完整成品，先列出待處理項。

第二部分的候選 ZIP／比較 PDF 仍是另外的下載功能，不和「最終成品」混淆。PNG 封存採低壓縮或 store 模式；生成 PDF 遵守既有包裝器、欄位次序及不額外視覺驗證的規則。

### 刪除項目

- 顯示項目名稱、資料量及將刪除的範圍，要求一次明確刪除確認。
- 執行期間不能刪除：包含偵測、修復、保存、封存與正在讀取下載的資產；檢查與開始刪除需使用同一項目鎖，防止檢查後又啟動任務。
- 刪除項目擁有的原圖、編輯、結果、日誌與快取；只移除明確屬於該項目的 job，不波及其他項目、歷史未歸屬 job 或模型。
- 記錄 deleting 狀態，清理失敗可重試；不能只刪清單條目而把大型圖檔留在磁碟。
- 不做自動按天清理；使用者從項目列表刪除舊項目。

| P0 項目資料契約 | Project/Page/Revision/Run/Composition 格式、目錄與 API 定義；既有 jobs 相容方案 | 原圖、底圖、Mask、候選和成品有明確來源；直接匯入 Mask、全黑頁、重跑各有固定規則 |
| P1 項目基礎與第二部分接入 | 項目列表、新建、原圖／Mask 匯入、保存重開；新增 project/snapshot 引用接既有 engine | 能建立項目，直接用 Mask 進既有第二部分；重開不丟資料；舊任務仍可查看／下載 |
| P2 共用畫布與第一部分人工編輯 | 縮圖、縮放平移、矩形筆刷、F1/F2、撤銷重做、自動保存、配對導出 | 原尺寸座標正確；保存後重開一致；人工擦除保護；輸出底圖和 Mask 與確認版本一致 |
| P3 第一部分 GPU 偵測 | RF＋MangaLens 核心遷入、依賴隔離、模型配置、統一 GPU 排程 | 兩模型真實 CUDA 推理；正確分類；重新偵測保護人工決定；與修復模型切換後無显存衝突 |
| P4 第三部分比較合成 | 完成 run 入口、同步比較、差異 Mask、局部來源採用、羽化、保存與成品 | 同一頁能混用不同候選；重開保持採用結果；全黑頁齊全；預覽與原尺寸導出一致 |
| P5 封存與項目生命周期 | 完整項目導出／匯入、成品 ZIP、刪除與用量、文件和鏡像整合 | 換目錄匯入仍可編輯；成品齊頁；刪除範圍正確；發布鏡像不含項目資料 |

依賴：P0 → P1 → P2；P3 與 P4 在資料和畫布接口固定後可由子代理分工，P5 集成收尾。GPU 推理只由單一調度執行，開發分工不表示並行載入模型。模型尚未上傳時，可完成 P0/P1/P2、用已有候選完成 P4，以及 P3 的非推理部分；P3 CUDA 驗收等待真實權重與目標 GPU，不用模擬結果代替。

建議後續子代理分工：一位負責項目資料／封存，一位負責 RF＋MangaLens 純核心與執行器，一位負責比較合成核心；主代理負責共用前端畫布、既有第二部分銜接和集成。先界定各自檔案與接口，避免多人同改 App.tsx、schemas 和 engine。

### 預計程式位置

- `frontend/src/`：拆出項目列表、項目工作台、共用畫布、前處理及合成面板；保留既有批量元件和互動。
- `backend/app/`：新增項目儲存、修訂、圖片服務、編輯、合成及封存模組；擴充 schemas/API 與 engine 調度。
- 本倉庫自有影像核心套件：移入去 Qt 的純色分類、RF/MangaLens adapter、差異與合成函式。
- `config/`：新增可選偵測模型與依賴清單，不改三份固定生產工作流。
- `backend/tests/` 和前端必要測試：涵蓋資料、圖像規則、操作座標及整合邊界。
- 行為落地時同步更新 `AGENTS.md` 的舊批次 UI／資料規則，以及 README、ARCHITECTURE、DEPLOYMENT、RELEASE；本計劃不把尚未實作內容寫成現況。

## 11. 驗證與交付邊界

不重跑已被使用者確認可用的原第二部分作為起點。只針對新增或改動的邊界驗證：

1. 資料：stem 衝突、Mask 尺寸／方向、來源快照、舊 jobs 相容、保存競爭與斷線恢復。
2. 圖像：兩類互斥、顏色保存、重新偵測保護、縮放後筆刷座標、差異 Mask 與來源分配、羽化與原尺寸導出。
3. 完整性：混合普通／全黑 Mask，全部全黑不啟動推理，結果齊頁；項目封存移到另一資料根目錄重開；活動任務／下載與刪除互斥。
4. GPU：新模型和環境初次接入先一頁 smoke test，再測受影響流程的小批次；記錄模型載入、推理、切換耗時和显存。更改輸入轉換或 Mask 契約時驗證受影響的既有修復路徑，不能因第二部分先前可用就跳過新增接口回歸。
5. 開發檢查：程式修改後執行既有 lint、build、後端測試和適用的 verify-local；純計劃文件不需要啟動服務或執行 GPU 測試。

GPU 測試、遠端部署、模型上傳與鏡像發布是後續交付活動。制定本計劃時不進行實作；使用者後續指示「開始」並要求新分支後，已進行本機實作與驗證。未進行模型下載、開關機、部署、提交或推送。
